# EMHASS Lens

EMHASS Lens drives [EMHASS](https://github.com/davidusb-geek/emhass), and you can watch everything it does:

- **Inputs:** it builds the price, PV and battery inputs.
- **Scheduling:** it runs the MPC optimization every quarter-hour.
- **Publishing:** it publishes the plan as each slot starts.
- **Records:** it keeps every run, payload, EMHASS response and log line.

## Getting started

1. Start the App and open **EMHASS Lens** from the sidebar.
2. Go to **Settings** and work through the sections:
   - **EMHASS**: the address of your EMHASS App. Leave it empty to look it up automatically. The mode starts as **Off**.
   - **Inputs**: the entities for battery state of charge, the target SOC and your deferrable loads (e.g. EV charging).
   - **Prices**: your Elektrilevi network package and the other fees.
   - **Price forecast** and **PV forecast**.
3. Switch the EMHASS mode to **Dry run** to see the payloads EMHASS Lens would send, without sending them. The mode switch is in the status chip at the top right ("OFF · Nobody drives"): click it.
4. When the dry runs look right, switch to **Live**.

## Finding your way around

- **The tabs** under the top bar list the pages in groups, a thin line between them: **Operate** (Plan, Inputs), **Control** (Inverter, EV charger, Market, all experimental), **Diagnose** (Runs, Logs, Health) and **Configure** (Settings). Where they don't fit (on a phone) they scroll sideways. Hover a tab for its keyboard shortcut (g, then a letter); ⌘K or Ctrl K searches pages, runs and settings.
- **The status chip** at the top shows the EMHASS mode and who drives EMHASS, for example "LIVE · EMHASS Lens drives". Click it for the mode switch, the next MPC run, the state of every part (Home Assistant, EMHASS, prices, forecasts, MQTT…) and the live-update connection. Its colour follows the mode: green for Live, blue for Dry run, grey for Off, red when the HACS integration and EMHASS Lens both drive.
- **Problems**: when something needs attention a red or amber "N problems" chip appears next to it and opens the list on Health.
- **Run MPC now** builds the payload and runs it straight away, as the mode says, and opens the run.
- **⌘K** (Ctrl+K on Windows and Linux) or the search field opens a palette: type a page, a settings section or an action, or a run number to open that run or its logs.
- **Shortcuts**: press **g** and then **p** (Plan), **i** (Inputs), **r** (Runs), **l** (Logs), **h** (Health) or **s** (Settings).
- **One notice at a time** shows under the top bar (for example "EMHASS Lens was updated or restarted"); when there are more, **+N more** shows the rest.

## Modes

| Mode | What happens |
|---|---|
| Off | Prices and forecasts are kept up to date; EMHASS is never called. |
| Dry run | Every quarter-hour the MPC payload is built and validated and shown under **Runs**, but not sent. |
| Live | The payload is sent to EMHASS, the plan is read back and published at the start of each slot. |

## Moving over from the HACS integration

While the [HACS integration](https://github.com/anton4/homeassistant-ee-nordpool) still runs, EMHASS Lens works next to it:

1. **Enter the settings.** Copy the integration's tariffs into **Settings → Prices**, and its eupowerprices.com API key and forecast choice into **Settings → Price forecast**.
2. **Shadow mode (mode Off).** Every quarter-hour EMHASS Lens builds the MPC payload it would send. The *parity* check compares prices, PV and payloads with the integration's entities and labels the differences that are intended, for example the corrected EV deadline.
3. **Dry run.** EMHASS Lens also runs every check a live run would, such as whether EMHASS is reachable, whether its configuration is compatible, and whether nobody else is driving EMHASS.
4. **Take over** (Health page). This turns the integration's *EMHASS Auto MPC* switch off and switches EMHASS Lens to live with Auto MPC on, in one step. **Hand back** does the reverse.

EMHASS Lens refuses to run live while the integration's Auto MPC switch is on, so two planners never drive EMHASS at once.

## Home Assistant entities (MQTT)

With **Settings → Home Assistant outputs → MQTT entities** on, EMHASS Lens publishes an *EMHASS Lens* device through the Mosquitto broker App:

| Entity | What |
|---|---|
| `sensor.emhass_lens_import_price` | Import price now, €/kWh for the current 15-minute slot. Attributes: next slot price, period (day/night/peak), spot. |
| `sensor.emhass_lens_export_price` | Export price now, €/kWh |
| `binary_sensor.emhass_lens_problem` | On while something needs attention. The attributes list what. |
| `binary_sensor.emhass_lens_hold` | On while a market session holds the inverter (see *During a market session*). Attributes: the entity, its value, since when, the last resume. |
| `sensor.emhass_lens_last_mpc` | When the last live run produced a plan |
| `switch.emhass_lens_auto_mpc` | Pause or resume the scheduled MPC runs, e.g. from an automation during an mFRR session |
| `button.emhass_lens_run_mpc` | Run MPC now |

The entities are retained on the broker, so they survive Home Assistant restarts.

If EMHASS Lens can't reach the broker for 2 minutes, Health shows *MQTT entities aren't being updated* with the reason: no Mosquitto broker App found, the broker refused EMHASS Lens's login, or the broker can't be reached. Connecting after a start or after switching MQTT entities on doesn't count.

## The plan-published event

In live mode EMHASS Lens publishes the plan right after each slot starts. It calls EMHASS's `publish-data`, then fires `emhass_lens_plan_published` with the current slot's values:

```yaml
event_type: emhass_lens_plan_published
data:
  slot_start: "2026-10-09T11:15:00.000+00:00"
  current: {p_batt_w: -11143, p_grid_w: 0, p_pv_w: 12928, p_pv_curtailment_w: 0, soc_opt: 0.496}
  price: {import: 0.1672, export: 0.0351}
```

**When an MPC run fails.** A failed optimisation replaces EMHASS's latest result, and EMHASS then refuses to publish. Live MPC runs therefore ask EMHASS to save the sensors of every good plan (`entity_save`). While the last live run has failed, the publish has EMHASS post those again (`publish_prefix: all`), so `sensor.p_*` and the event carry the last good plan's values for this slot, and the event's `republished_because` says why. Once that plan is older than the plan max age (Settings → Health, 2 slots), the publish is refused with the reason instead, and the inverter is left in its last mode, as with any stale plan.

An inverter-control automation can trigger on this event instead of on a fixed second after the quarter-hour. Keep the old time trigger as a fallback. If your automation only writes changed values, the second run is a no-op:

```yaml
triggers:
  - trigger: event
    event_type: emhass_lens_plan_published
  - trigger: time_pattern   # fallback if the event doesn't come
    minutes: "/15"
    seconds: 30
mode: queued
```

## What EMHASS gets

The top of the Inputs page shows the payload of the newest MPC run, slot by slot from its anchor to the end of the horizon. **Preview now** shows one built as if a run started now instead; nothing is sent. Cards sum it up, each with the payload keys it stands for: the horizon, how many prices are Nord Pool's and how many a forecast, the PV energy, the battery's state of charge now and its target, how EMHASS forecasts the house load, and the deferrable loads. Under them, four charts on one time axis:

- **Prices sent**: the import and export price, forecast prices shaded. Under the chart, the tariff period (day, night, peak) and the export limit, hatched where export is capped at 0 W (Settings → EMHASS → MPC → *No export at or below*).
- **PV forecast sent**: Solcast's estimate (the one Settings → PV forecast → *Estimate* picks), with each day's total above its hump. PV held back for the EV reserve shows as its own area.
- **House load**: EMHASS forecasts the house load itself, with its ML model trained on the last days of the load sensor (`var_model`); EMHASS Lens doesn't send a load forecast. The chart shows the forecast from EMHASS's plan, and under it each deferrable load's window up to its deadline, hatched when the load is off and sent as 0 W.
- **Battery**: the state of charge sent at the anchor and the target at the end of the horizon.

**Before the anchor: 24 h measured** adds the last 24 hours, shaded. The house load (from your load sensor), PV and the battery's state of charge are as EMHASS Lens measures them (Settings → Measurements), so you can see the measured load run into EMHASS's forecast. *Prices sent* shows the Nord Pool prices that applied, with today's tariff and their tariff periods; nothing is sent to EMHASS for past slots. Pointing at any chart shows the Plan page's popup on every chart at once: the quarter-hour, whether it is measured or sent, and every value, with the tariff period, export limit and deferrable loads under a rule. A drag zooms in; a double-click shows everything again.

**After the horizon: Forecast** adds what comes after the plan's end, shaded, as it is now and not sent: the price forecast (with the most days eupowerprices.com has, up to 7) and Solcast's PV forecast, with each later day's total marked *not sent*. The **Horizon** lane under *Prices sent* shows what was sent and, hatched, what wasn't. **Plan length** picks how many days of the price forecast the plan takes after the Nord Pool prices (Settings → Price forecast → *Extend by*). Point at a choice to see in the Horizon lane where that plan would end with today's data; a choice the forecast doesn't reach is greyed out. Clicking one asks first and then saves it for the next MPC run (*Preview now* shows it right away). A longer plan gives EMHASS's load model more lags (192 + 96 per forecast day, unless set under Settings → EMHASS → ML), so the model is fitted again after the next run when *Fit on fault* is on.

## Prices and your own price sensors

EMHASS Lens fetches Nord Pool's day-ahead prices itself and prices every quarter-hour with the fees, Elektrilevi network package, night hours, holidays and VAT under **Settings → Prices → Tariff**; the Inputs page shows the breakdown per slot. Its **Prices** section has the import, export and spot price over every day loaded, and right under it, on the same time axis, what the import price is made of: a column per quarter-hour of spot, network, fees and VAT stacked (blue, aqua, yellow, magenta), with the import price as a dark cap on top, each day's cheapest and dearest quarter-hour named, and forecast quarter-hours faded (switch parts off under the chart). Point at either chart and both show a popup for the quarter-hour under the pointer, and the column is ringed: the prices, whether they are Nord Pool's or a forecast (and whose), and the parts with the rate (day or night). **All days**, **Yesterday**, **Today** and **Tomorrow** zoom both charts and pick the day of the table under them; a drag zooms in, a double-click shows every day again. It does not read Home Assistant price sensors. If you keep Nord Pool template sensors with fees for dashboards or automations, **Settings → Prices → Compare with your price sensors** names them (a sensor with a `raw_today` / `raw_tomorrow` or `raw_all` attribute of `{start, end, value}` in €/kWh including VAT), and the parity check (every quarter-hour at :05, Health → Parity checks) compares them with the App's prices slot by slot. A difference that is the same for every day slot and every night slot is explained in words, for example a template still on Elektrilevi Võrk 2 rates while the contract is Võrk 4. The Home Assistant Nord Pool integration rounds the spot price to 3 decimals (the `3` in `sensor.nordpool_kwh_ee_eur_3_10_0`), up to 0.05 c/kWh; the comparison rounds the App's spot price the same way, so only real differences show (Settings → Prices → Compare with your price sensors → *Spot price decimals*).

**This slot** on the Plan page shows the plan row in force for the current quarter-hour (the plan published at its start), with **Previous slot** for the one that just ended and **Next slot** for the one after. It is drawn as a flow: PV at the top, the grid on the left, the battery on the right, the house and the EV below. The lines are as thick as the power and point the way it flows, and the line at the top says in words what happens ("Charging the battery from the grid"), with the inverter's passive mode next to it in its Inverter-page colour (hover it for the full mode). A source is named only for the power that reaches what it feeds, and only when it adds 300 W or more: PV covers the house first, so "from PV and the grid" means the grid really charges the battery, not that it runs the house while PV charges the battery. The words change only once two reads in a row (10 seconds apart) agree, so the few seconds of import while the inverter catches up with a load that just switched on don't flip them; the boxes always show the latest reading. Each box shows what the sensors under Settings → Measurements read now as the big number, with the plan under it ("plan 12.69 kW"), and next to its name how long ago that sensor last changed. The line under the headline gives the slot's times; hover them for when the slot was published and when the page last read it (every 10 seconds). Where nothing is measured, the box shows the plan and says *planned* or *forecast*. The EV's power is its charger's current limit while it charges, and the time next to its name is when the charging state (or, while it charges, the current limit) last changed. The Battery and EV boxes show the state of charge beside the power (on a phone, at the end of the line under it): the battery's from Settings → Measurements, or the plan's for the end of the slot when nothing is measured, and the car's from Charger entities → Car battery level, with its target in the hover text. Beside the flow are the battery's state of charge (measured, with the plan's range for the slot as a bracket and EMHASS's minimum hatched) and the slot's prices, with where the import price sits among today's. Only what the inverter controls is judged, against what the plan means with the house load, PV and EV charging as they are now. The battery and the grid are compared with where the inverter's passive settings put them: it holds the grid at its target and the battery covers the rest within its window, so in PV export (the battery may not charge) more PV than forecast is exported, and in a force discharge the battery covers whatever the house really uses. The settings are the inverter's registers now, or for the previous slot what the inverter rules give its plan row; without inverter control the grid is compared with the plan and the battery takes the difference. Where that expectation is off the plan the box shows it under the plan ("expected 4.44 kW"). The state of charge is compared with where the plan expects it at this moment. An amber edge means a difference of more than 300 W and 15 % (SoC: 2 points), and the chip at the top then names what differs, with the plan's own line ("Plan: the battery covers the house") under it. When everything does what is expected but that is off the plan, the chip is blue and says why: "More PV and less house load than forecast" (or the inverter's settings). House load and PV are forecasts: shown, never judged; one that missed by 300 W or more has its forecast in blue. When the battery runs the other way than expected, the card suggests ticking *Opposite sign* for the battery sensor: EMHASS counts discharging as positive, most inverter sensors count charging as positive. **Inverter set to** shows the Sofar's passive settings (grid target, battery window, feed-in limit; the mode is the chip next to the headline) and when EMHASS Lens last wrote them, or why it isn't in control; the EV box shows what the charger is doing. **Previous slot** judges the slot that just ended the same way, against the quarter-hour means of the Measurements sensors (they appear shortly after the slot ends), with the state of charge compared half-way through the slot.

The Plan page says why when EMHASS's last run didn't end "ok" (EMHASS's own error message, and whether the plan shown is older than that run), and says so when EMHASS Lens didn't request the plan shown: someone else did (EMHASS's web UI, an automation or script, or the HACS integration with Auto MPC off), or the HACS integration while its Auto MPC switch is on.

## Plan history and accuracy

The Plan page opens with the plan in one line, for example "Discharging the battery until 21:30, then idle · SOC 94 % → 38 %": what the battery does from now until that changes, and where its charge goes meanwhile. The row above the flow holds the plan's facts (**Mode**, **Planned at**, **Solve took**, **Horizon**) next to the Previous/This/Next slot switch. *by HACS* after the time means the HACS integration's Auto MPC switch requested the plan. **Mode** says what drives the inverter now. *EMHASS* means the plan does. *Market* means a Qilowatt session holds the inverter, run by EMHASS Lens (Qilowatt market control on Live) or by your Home Assistant automation (seen through the market session hold, or market control on Shadow); its direction, power, source and start time follow. *market not watched* means neither is on, so a session could hold the inverter without EMHASS Lens seeing it. The facts row also includes the **Total cost function**: the sum of the plan's cost function column over its horizon, the value EMHASS publishes as `sensor.total_cost_fun_value` (EMHASS's sign: positive is money in). When the plan is older than Settings → Health → **Plan is stale after**, a note says how old it is and when MPC last succeeded, and the plan ahead is hatched (*plan too old*) on the charts.

The **Timeline** starts with a line that says what it shows: measured until when, how fine the grid's readings are ("every 10-second grid reading from Home Assistant"), then the plan from which run, and the time zone. Power, state of charge, price and the **MPC runs** share one time axis, under the last of them, with a pill at the now line ("now 15:32") and one at the cursor (to the second left of now). A hairline marks each midnight. Right of the now line everything is the plan: drawn fainter, on a light wash. Each chart's head has a key and adds up the window shown: **Power** what was imported and exported and what PV made, **Battery state of charge** where it is now and where the plan takes it, **Price** the cheapest and dearest quarter-hour (and the range of the ribbon under the chart, which colours each quarter-hour's import price from light, cheap, to deep violet, dear, over the window shown). Forecast prices are hatched.

**Power** is one chart: PV and the battery discharging are stacked above zero (into the house), the house load, the battery charging and the deferrable loads below it (out of the house), per quarter-hour, and the **Grid** is a line on top: it is whatever those leave uncovered, importing above zero and exporting below. Point at a chart and each chart shows its own popup at that moment, one value per row, value first: the moment ("Fri 16 Oct · 13:25:20 · 10 s reading", left of now) or the quarter-hour, whether it is **measured** or **plan** (for prices: **Nord Pool** or the forecast's source), and each value with its name; what the plan said at the time is a row of its own under the grid, named after the plan **Compare with** picked ("planned then", "planned 6 h ahead"), and a rule parts the grid's rows from the flows. The chart you point at marks the row nearest the pointer. Battery and grid carry their sign: the battery is **+** when charging and **−** when discharging (unlike EMHASS's own sign), the grid **+** when importing and **−** when exporting. Every quantity has its own colour: the state of charge is teal (not the battery's blue), import violet and export green. The **MPC runs** are blocks, each from a run's start until the next one starts, coloured by outcome, with the next run outlined; a chip at the cursor names the run, a click opens it, and the strip's head counts the runs and says when the next is due.

The chips under **Power** switch its lines on and off (a quantity's measured, planned and planned-then lines together); the choice is remembered in this browser.

When Settings → Measurements has a grid power sensor, the **Grid** line left of now is every reading of that sensor (every 10 s on a typical meter), in one line with the plan right of now (in the quarter-hour in progress the plan's line starts at now). The popup's **Grid** row reads that line at the pointer, with the quarter-hour's mean on a row under it, and a dot sits on the line at the cursor. On a wider window the App averages over 10 s to 15 min so the chart stays quick, and each mean brings the lowest and highest reading behind it: the line is drawn through them, so a spike still shows, and the popup gives them on a row of their own. Each mean stops and starts again where a market command starts, ends or changes power. The App keeps the last eight days of readings in memory, so *7 d* shows them too: after a start, the run *Grid readings* reads the week from the recorder, newest first, and until it is done the chart fills in as the hours arrive. Stretches the recorder has no readings for are hatched (*no readings*) and named under the chart. Short peaks (a kettle, the car starting) widen the power axis.

When Qilowatt sent market commands in the window, the Power chart shows them under **Market**. They come from the Home Assistant recorder's history of the source, command and power-limit sensors (Settings → Qilowatt market control → Market entities), so they show whoever ran the sessions: EMHASS Lens, your automation, or nobody (market control off or on Shadow). A command is what market control reads as one: a known source with a buy or sell command and a power above zero; whether a session followed (the start threshold, the SoC floor) isn't judged. Back-to-back commands in one direction make a session. Its product comes from the command: *mfrr…* is mFRR, *frr…* aFRR.
- **Sessions:** each session is a band across the chart with an edge along its top, green for a sell and blue for a buy (an aFRR session hatched), with a flag above it: **↑** for a sell (up-regulation) and **↓** for a buy ("↑ SELL · mFRR · 5.2–9.4 kW"; point into the session for its source, times and how much was delivered), and a bar in the row under the chart with the share of the energy asked that the grid delivered ("95 %", more where it fits). Sessions of one direction whose flags would run into each other share one flag ("↓ BUY · mFRR · 15.5 kW +1"); where a flag has no room even short, it goes to a second row, each flag with a stem down to its session. Click a flag or a bar to zoom to its sessions. While the pointer is in a session, the quarter-hour lines fade. The key says when no session falls in the window.
- **Baseline and target:** a session is judged from its **baseline**, the grid's mean over the minute before its first command (Settings → Qilowatt market control → Thresholds → **Baseline**; 0 judges against zero). The command puts the grid at the baseline less a sell's power (plus a buy's): that is the **commanded target**, a dashed dark line stepping at the commands' own times. What was delivered is how far the grid moved from the baseline. (The inverter is always written the command's own target; the baseline changes what is shown.) The power axis fits the measured and planned lines, not the commands: a target past it runs along the top or bottom edge, labelled with its direction and power ("↓ 15.5 kW"). Where the grid delivered less than the command by more than 500 W or 10 % of it (whichever is more) for a minute or longer, the gap between the two lines is hatched red, the same stretch is hatched in the session's bar, and the key under the chart shows **Shortfall**.

Left of now, the popup's header is the moment under the pointer and the quarter-hour heads the rows below it. Inside a command, a block names the session ("↑ SELL · mFRR", its source and command) and says what was delivered ("9.97 of 10.00 kW delivered (100 %)") with a meter, the shortfall where there is one, and the session in two lines; the commanded target and the baseline are rows under the grid's reading. Without a grid power sensor it shows what the grid delivered over the whole command instead (the mean over its exact start and end).

The Plan page's charts reach back in time as well as forward. Left of the now line they show what was measured; right of it, the current plan. **Window** picks how much time they show around now: *8 h* (the default: 4 h back and 4 h ahead, where every 10-second grid reading gets about two pixels), *24 h*, *2 d* (the last day and the whole plan), or *7 d* back to the end of the plan. The charts follow the clock while **Following now** is pressed. Scroll over a chart to zoom in or out around the pointer; hold Shift and scroll (or scroll sideways), or Shift-drag, to move; drag across a chart to zoom into that stretch (its times show over it while you drag; Escape cancels); or drag the box in the **Overview** under the charts (its edges widen or narrow it, and a chip names the window while you drag). **Back to now**, or a double-click on a chart, returns to the window around now. With the keyboard, Tab to the Power chart: ← → move the cursor (10 s within 2 h, else a quarter-hour; with Shift 5 min or an hour), + and − zoom, Page Up/Down move the window, Home goes back to now, Escape puts the cursor away; every chart's popup follows, and a screen reader hears the values. On a phone (a screen under 640 px wide) the Timeline has its own charts: **Grid** (its readings and the market's sessions), **Power balance** (the same flows with the grid stacked as a layer of its own, import on top and export at the bottom, so both sides add up), **State of charge** and the **Import price**; each shows its values in a chip at the cursor. Its windows are *4 h* (3 h back, 1 h ahead), *24 h* and *2 days*. Drag along a chart to read it, pinch to zoom and move two fingers to move. **Compare with** picks which earlier plan a past slot is held against: *Plan in force* is the plan that was current when the slot came (what the inverter followed), *1 h / 6 h / 24 h ahead* the plan made that long before it, which shows how good the forecasts were at a distance.

Under the charts, **Table view: the 6 hours around the cursor** lists the quarter-hours around where you last pointed (grid, PV, house, battery, SOC and the prices; measured left of now, the plan right of it), and **Every column of this plan** is the whole plan as a table, one row per quarter-hour (columns in words, with EMHASS's own names under them; power in kW, SOC in %, prices in €/kWh).

Measured values come from Home Assistant's recorder. **Settings → Measurements** names the sensors for grid power, battery power, PV power, house load and battery SOC; leave one empty to skip it. Signs follow EMHASS: grid positive when importing, battery positive when discharging. If a sensor counts the other way round, tick **Opposite sign**; **Multiply by** turns kW into W or a percentage SOC into 0–1. The House load sensor should be the load *without* deferrable loads (what EMHASS forecasts as `P_Load`), usually the same sensor EMHASS learns from.

Every quarter-hour the run *Measurements* reads the slot that just ended and stores its time-weighted mean per quantity. After a start, and after a change under Settings → Measurements, *Measurement history* reads older history in six-hour chunks (newest first) back to **Read history back** days, the recorder's reach (10 days by default in Home Assistant). Measurements are kept for **Keep measurements** days in `app.db`.

**How accurate the plan has been** (under the charts) gives, per quantity, the mean absolute error with the bias under it (plan minus measurement; plus means the plan expected more) over the last 24 hours and 7 days, the load error also as a share of the measured load, and the price forecast's error against Nord Pool's price for the forecast fetched 24 hours before each slot. When grid or battery power moves against the plan most of the time, the card says so: that nearly always means the sensor's sign is the reverse of EMHASS's.

## Cost functions

EMHASS can optimise for one of three things, its `costfun`: **profit** (import cost minus export revenue, EMHASS's usual default), **cost** (import cost only, exports earn nothing) or **self-consumption** (use as much PV on site as possible). **Settings → EMHASS → MPC optimization → Cost function** picks the one every live run asks for; *EMHASS's own setting* sends nothing and leaves EMHASS's configured value in charge. The cost function is a runtime parameter since EMHASS 0.18; the plan read back shows which one EMHASS used, and Health warns if it was ignored.

**Cost functions** on the Plan page compares the three. **Compare now** runs the MPC three times with the same inputs, once per method, and shows what each would do with the battery and the grid and what it would cost over the plan's horizon: net cost, import and export, self-consumption, battery throughput, end SOC, and EMHASS's own objective total (the sum of the plan's `cost_fun_*` column, in EMHASS's sign, only comparable within one method). One chart overlays the three plans for a chosen quantity, with each method switchable on and off; a table below lists earlier comparisons. **Compare cost functions on every run** does the same before every live plan.

Every optimisation replaces EMHASS's latest plan, which publish-data and the plan API read, so the method in use always runs last and EMHASS ends with the real plan; the plan watch and publishing wait while a comparison runs. A comparison is refused while the mode is Off, EMHASS is unreachable, the HACS integration still drives EMHASS, an ML fit runs or a market session holds the inverter. Two extra optimisations take a few seconds to a minute each; if publishing gets tight, move the MPC time earlier under Settings → EMHASS → MPC optimization.

**Solver time limit.** EMHASS stops its solver after `lp_solver_timeout` seconds; when it gets there without a plan it tries a relaxed problem under the same limit and otherwise records an error with no message, so a timed-out run takes about twice the limit and leaves no plan. With Settings → EMHASS → MPC optimization → *Solver time limit* on *Auto* (the default), EMHASS Lens sends `lp_solver_timeout` with every optimisation, from the time left before the next slot's publish: the live plan gets most of it, each comparison step at most 30 seconds. When the live solve still stops at its limit, it is retried once with a looser MIP gap (5 %, *MIP gap for the retry*), which finishes much faster on long horizons; the run then says "after a retry with a 5 % MIP gap". MPC runs at 11:00 into each quarter (it was 13:00), which leaves about four minutes. *EMHASS's own setting* sends neither; `lp_solver_timeout` under Extra runtime parameters overrides both.

**Battery charge power derating.** EMHASS's `battery_charge_power_derating` (a lower charge power above a state of charge) gives the solver a yes/no variable for every step of the table in every slot. With two steps, a 52-hour plan took over 2 minutes on a Home Assistant host instead of a few seconds, and runs stopped at their time limit with no plan. EMHASS Lens therefore sends an empty table with every optimisation: the plan assumes the full charge power up to 100 %, the battery's BMS tapers the charge anyway, and every quarter-hour's plan starts from the real state of charge. The run's validation notes it. To plan with derating anyway, add `battery_charge_power_derating` under Settings → EMHASS → Extra runtime parameters.

**No export at or below a price.** Settings → EMHASS → MPC optimization → *No export at or below* (€/kWh) keeps EMHASS from planning any export in a slot whose export price is at or below it. Every run sends `maximum_power_to_grid` as a list with 0 W in those slots and EMHASS's own maximum elsewhere. It is a hard limit, so every cost function respects it. In those slots EMHASS charges the battery with surplus PV, curtails what it can't store (`P_PV_curtailment`), and doesn't discharge the battery to the grid. The inverter control uses the same value for its feed-in limit. Empty turns both off. It needs EMHASS 0.16 or newer with `compute_curtailment` on; otherwise the run says why it wasn't sent, and Health → EMHASS shows a warning. The Explain table's *Export max* column shows the blocked slots, and the parity check's comparison build leaves it out.

**When the live run after a comparison fails**, EMHASS is left holding the last alternative's plan: EMHASS's plan API keeps the last successful plan, and `publish-data` publishes the latest result. EMHASS Lens notices it, doesn't store or publish that plan, and Health shows *EMHASS holds a cost-function comparison plan* until a live run succeeds; meanwhile the inverter keeps the last live plan until it is too old.

## Inverter control (experimental)

EMHASS Lens can set a Sofar inverter's passive mode from the plan itself, instead of a Home Assistant automation doing it. It follows the automation "EMHASS: Consolidated Inverter Control" rule for rule, with a few deliberate differences described below: the plan's grid power picks the branch (importing, exporting or neutral), the battery power picks the mode (force charge, force discharge, use only grid, self-use, …), and when exporting with an idle battery the export price decides whether the PV is exported or kept. The feed-in limit for a slot is 0 W when the export price is at or below **Settings → EMHASS → MPC optimization → No export at or below**, otherwise the export maximum. The same value keeps EMHASS from planning exports in those slots, so in a blocked slot the plan shows no export and curtailed PV, and the rules pick *restrict export*. When the setting is empty, export is never blocked.

Unlike the automation, EMHASS Lens only writes the feed-in limit when something can reach the grid in the slot: the plan exports, curtails PV, or has PV to spare (PV above the house load) while its state of charge for the slot is at or above **Settings → Inverter control → Battery counts as nearly full at** (90 %). Otherwise the limit is left as it is. A battery with room to spare takes the spare PV, and in passive mode with a grid target of 0 it doesn't feed the grid. Every press of the feed-in button is an EEPROM write, and with prices around the threshold the price alone would flip the limit many times a day. A limit left as it is isn't compared with the automation in dry run and isn't set back by the drift check. The decision shows *unchanged* and says why. When export is allowed, a limit that already lets out what can reach the grid (the plan's export or spare PV, rounded up to 100 W) is kept as well, for example the one a market sell session left behind: it isn't rewritten to the export max, and the drift check doesn't set it back. Only a lower limit is set back to the export max.

The passive battery window (battery power min … max) follows Sofar's sign, where charging is positive: the opposite of EMHASS's `P_batt`. So *Use only grid power* (0 … 20000 W) lets the battery charge but not discharge: PV still feeds the house first, the grid covers the rest, and surplus PV charges the battery. The plan's battery power counts as idle within ±100 W, so a slot planned with a few tens of watts from the battery gets this mode too.

**Where the plan mixes grid and battery.** With a grid target of 0 W the battery takes all the slack, which is what the plan wants in most slots. Two rules are different:
- *Use the battery, import the rest* (importing and discharging): the plan is saving the battery's energy for a dearer slot, but the battery would cover the whole house.
- *Charge and export* (exporting and charging): the plan is selling some PV now and leaving room to fill the battery later, but the battery would take all the surplus and nothing would be exported.

With **Settings → Inverter control → Use the battery, import the rest: cap the discharge at the plan** and **Charge and export: cap the charge at the plan** (both on by default), the battery window stops at the plan's battery power plus half of **Battery cap slack** (500 W), rounded up to 100 W. The battery then gives or takes what the plan says, and the grid covers the rest or takes the export. The charge is never capped in a slot at or below *No export at or below*: there the feed-in limit is 0 W, so capped PV would be curtailed instead of stored. A cap already on the inverter is kept while it is 0–500 W above the plan, so the apply button (an EEPROM write) isn't pressed every time the plan moves a little. A drift correction sets back the plan's own cap. Turn either setting off to do what the automation does; until then, dry run differs from the automation in those slots.

| Mode | What happens |
|---|---|
| Off | Nothing is decided. |
| Dry run | Right after each publish the decision is recorded (rule, why, targets) and 40 s later the inverter entities are read and compared with it. The **Inverter** page shows the agreement over 24 h and 7 days. The inverter is never touched. |
| Live | EMHASS Lens applies the decision itself (the passive-state select, the three passive-mode numbers and their apply button, the feed-in limit and its button) and reads them back. Only values that differ are written. |

Nothing is written while the inverter isn't in passive mode, while the automation switch (`input_boolean.emhass_automation`) is off, for example during an mFRR session, or when the plan is stale.

**When Home Assistant restarts.** While Home Assistant is away, the quarter-hour publish fails and the inverter and EV charger decisions are refused; the inverter keeps the settings it last got. A restart also drops EMHASS's `sensor.p_*` states. When Home Assistant answers again (after a restart, a host reboot or a lost connection), EMHASS Lens catches up the current quarter-hour in live mode: it publishes again (which brings `sensor.p_*` back and fires `emhass_lens_plan_published` once more), then decides the EV charger and the inverter for this slot. If the inverter's entities are still loading, it retries every 20 seconds for up to 5 minutes, within the slot; a stale plan or another inverter mode ends it. Runs started this way show *(catch-up after Home Assistant came back)*.

**Kept in sync every minute.** In live mode EMHASS Lens compares the inverter's passive-mode settings and feed-in limit with what it set for the slot every minute, and sets back what something else changed (an automation, the Sofar app, an inverter restart). It writes only the settings that differ, never within 2 minutes after its own write (Home Assistant may still show the old value), and only when the difference is seen twice in a row at least 30 seconds apart. After 3 corrections of the same setting within an hour it stops for an hour and Health shows *Something else keeps changing the inverter's …*, so the two don't keep pressing the apply button, which writes the inverter's EEPROM. Corrections appear under Runs as *Drift: grid power 3000 W, expected 5600 W; set back*, and the Inverter page shows *Kept in sync*. Turn it off under Settings → Inverter control → *Check every minute and set back what drifted*.

**On the Inverter page** the switch at the top sets the mode (Off, Dry run, Live) without going to Settings; it asks first, and switching to Live reminds you to turn the automation off. Under it, **Today, slot by slot** shows every slot of the day coloured by the passive state it set (the key above the strip names them), hatched where EMHASS Lens wasn't in control, with the state named where it changes. The line under the strip is light green where the automation did the same and amber where it differed (dry run), or dark where a slot wrote to the inverter (live). Point at a slot (or tap it on a phone) to see its five Sofar settings: passive state, grid power, battery min, battery max and feed-in max, which of them changed since the slot before, and what the automation set where it differed; click a slot to open its decision.

A slot during which EMHASS Lens's own market session held the inverter (Qilowatt market control on Live) is drawn in the colour of the state the session set (Force discharge for a sell, Force charge for a buy) with white stripes, and named *Market sell* or *Market buy*. Its popup names the session (direction, power, source, start and end). Every slot's popup also lists what EMHASS Lens wrote to the inverter in it, in order, for the plan or for the market: grid power, the battery's range and the feed-in limit, each with its run. Clicking a market slot opens the market run that wrote in it, or the one that opened the session. **Inverter writes** at the top opens the Runs page filtered to every run that wrote to the inverter. **How a rule is chosen** names the rule chosen for this slot and folds away the full list, in the order the rules are tried, grouped by what the plan's grid power picks (importing, exporting, neutral); *More about decisions* lists where EMHASS Lens differs from the automation. The EV charger and Market pages work the same way, decision by decision: consecutive decisions with the same outcome make one block, coloured by what it did, with a key above the strip that counts the decisions of each kind. On the Market page a sell is in Force discharge orange and a buy in Force charge blue, both striped as on the Inverter strip; no action is grey, a session end slate, a decision not in control hatched and an ignored command amber. On the EV charger page the plan's charging is in the EV colour, excess-solar charging in PV's, a pause in a light shade of its mode's colour, the target-SoC stop in the state of charge's teal and nothing to do grey. The line under the strip is green where the automation did the same and amber where it differed on any of the block's decisions (Shadow, Dry run), or dark where a decision wrote to the inverter or the charger (Live). Point at a block to see when its decisions were made, what they were, and how many the automation agreed with. Click it to open its first decision, or the first where the automation differed.

**Button presses.** Every press of the Sofar apply and feed-in buttons writes the inverter's EEPROM, so EMHASS Lens records each one, whoever pressed it. A press made by EMHASS Lens links to the run that made it and says whether it was for the plan or for a market session. For any other press, Home Assistant reports who made it: *an automation*, or *a user* (in the UI or through a script they ran). The Inverter page shows how many presses there were in the last 24 hours and 7 days (the Market page shows the same counts). On today's strip each press is a dot on the top edge: red for a press made outside EMHASS Lens, dark for its own. Point at a slot to see its presses with their times. **Button presses** at the bottom of the page lists the last 7 days, with *Only outside EMHASS Lens* to hide EMHASS Lens's own. Presses made while EMHASS Lens wasn't running aren't seen. Presses recorded by earlier versions are attributed to EMHASS Lens when one of its writes came within 30 seconds, and are otherwise *not known*.

**Moving the automation over:** set the thresholds under Limits to the automation's values, run **Dry run** for about a week and watch the agreement. When it stays at 99 % or more, turn the Home Assistant automation off (keep it) and switch to **Live**. To go back, set the mode to Off and turn the automation on again.

## During a market session (mFRR)

When an aggregator such as Qilowatt takes the inverter for a Kratt or Fusebox activation, EMHASS Lens can stand back and take over again the moment the session ends.

With **Qilowatt market control** on **Shadow**, the hold is always on. It follows the market's **Session state select**, which the automation sets to `buy` or `sell` while it drives the inverter, so there is nothing to turn on. The market source alone isn't used: a command below the start threshold opens no session, and the source still names Kratt or Fusebox after a session ends. With market control on Live, EMHASS Lens runs the sessions and hands the inverter back itself. Without market control, turn the hold on under **Settings → Market session hold**:

- **Session entity** and **busy values**: the entity your market automation maintains, for example `input_select.qilowatt_session_state` with the values `buy` and `sell`.
- While the entity shows a busy value, MPC keeps planning every quarter-hour, but the plan isn't published and the inverter isn't touched. The Health page's *Driving EMHASS* card and `binary_sensor.emhass_lens_hold` show the hold.
- When the session ends, EMHASS Lens waits for the inverter control's enable switch to come back on (your automation hands it back), then publishes the newest plan once and decides the inverter from it. That plan was made during the session, so even a long session hands back to a plan at most a quarter-hour old. Only the registers that differ are written, so a session end costs at most one write to the inverter.
- **Re-run MPC after a session** (off by default) also runs MPC again with the battery state after the session and publishes that plan. The inverter keeps this slot's targets and follows the new plan from the next slot, so there is still only one inverter write.

Each resume is recorded as a run of *Resume after a market session*.

## EV charger control (experimental)

EMHASS Lens can drive an EV charger the way the automation "EV Charging: Combined EMHASS & Excess Solar" does, branch for branch. Your charge-mode helper stays the control, and the EV charger page can switch it (the buttons set the helper through Home Assistant, so the automation sees the same mode):

- **EMHASS**: follow the plan's EV power (`P_deferrable0`): start charging when the car is plugged in and the plan asks for power, adjust the current while charging, pause when the plan asks for none. The current is the planned power ÷ 690 W/A, at least 6 A and at most your maximum current.
- **Excess Solar**: every minute, charge with what the PV leaves over after the house load (the potential PV when the inverter is curtailing), rounded down to whole amps; never raise the current on PV data older than 10 minutes.
- **Manual**: nothing.

**Kept in sync.** In live mode, when the charger shows another current limit than EMHASS Lens set and nothing new was decided (the car's or the charger's app, an OCPP backend), the minute check sets it back: not within 90 seconds after its own write, only when seen twice in a row, and after 3 corrections within an hour it stops for an hour and Health says so. A new target from the plan or the sun applies at once as before. Settings → EV charger control → *Set back a current limit something else changed*.

Each decision under **Recent decisions** shows what it does (for example *→ limit 12 A*) and the numbers it was made from: the current before, and the PV, house load (with the charger's share) and surplus for Excess Solar, the plan's EV power for EMHASS mode, or the car's level and target for the SoC stop.
- In any mode: when the car's SoC has been at or above the target SoC for 5 minutes, stop charging, set the limit to 0 A, send a phone message and put the target back to 100 %.

Settings → **EV charger control** holds the entities (charger state, current limit, start/stop buttons, car SoC, target SoC, maximum current, PV, house load) and the limits. Settings → **Notifications → Mobile notify service** (e.g. `notify.mobile_app_my_phone`) is where the phone messages go; leave it empty for none.

| Mode | What happens |
|---|---|
| Off | Nothing is scheduled. "Decide now" on the EV charger page still shows what it would do. |
| Dry run | Every decision is recorded with the calls it would make and the message it would send, and a few seconds later the charger is read to see whether the automation did the same. The EV charger page shows the agreement. The charger is never touched. |
| Live | EMHASS Lens presses start/stop, sets the current limit and the target SoC, sends the message and reads the charger back. |

**Moving the automation over:** run **Dry run** for about a week with the automation still on and watch the agreement. Then set the automation's entity under Charger entities → *Home Assistant automation (interlock)*, turn the automation off and switch to **Live**: EMHASS Lens refuses to act while that automation is on, so the two never both drive the charger. To go back, set the mode to Off and turn the automation on again.

### Reserving PV for Excess Solar

In Excess Solar mode the car takes the PV surplus outside EMHASS's plan, and EMHASS, which still sees the full PV forecast, may plan to fill the home battery or export with energy the car will use. EMHASS has no input for that, so **Settings → EV charger control → PV reserved for Excess Solar** lets EMHASS Lens send it a smaller PV forecast instead. While the charge mode is Excess Solar, the car is plugged in and its SoC is below the target, every slot's PV forecast is reduced by what the charger is expected to take: the Excess Solar rule applied to the PV forecast minus the house load EMHASS itself forecasts for that slot (the `P_Load` of the newest plan), in whole amps, at least 6 A and at most the maximum current. Reserving stops once the energy from the car's level to its target is covered, which needs the **car battery capacity** setting; the rest of the horizon gets the full PV again. The Explain table of each run (and of the payload preview) shows the reserved watts per slot and a line saying how much was reserved and until when, and the EV charger page shows the current state. Nothing changes in EMHASS or Manual mode, in the parity check against the HACS integration, or when the controller is Off (the car's entities are still read). Because EMHASS plans with the smaller forecast, its plan's `P_PV` and the PV accuracy on the Plan page show the PV that was left for it, not the full forecast.

## Qilowatt market control (experimental)

Kratt and Fusebox activations (mFRR, aFRR) arrive through Qilowatt as three sensors: the source (`sensor.qw_source`), the command (`sensor.qw_mode`) and the power limit (`sensor.qw_powerlimit`). EMHASS Lens can run these sessions on the inverter the way the automation "Qilowatt: Master Market Controller" does: on every command change (after a short settle time), every minute and at start-up it derives the wanted inverter state from the current values and reconciles it with the registers, with three guards against needless writes to the inverter's EEPROM (a direction-aware hysteresis, a proportional deadband and a cooldown; a session end is never throttled). Unlike the automation, EMHASS Lens writes a gap that only the proportional deadband hides once it has held for the cooldown, so a command raised by less than 15 % still gets through within about three minutes. The **Market** page explains the guards with your thresholds and shows the live command, the session, each decision with its reasoning, and how many times the inverter's apply and feed-in buttons were pressed.

| Mode | What happens |
|---|---|
| Off | Nothing is watched. "Reconcile now" still shows what it would do. |
| Shadow | Every decision is recorded, and a few seconds later the session select, the EMHASS automation switch and the inverter registers are read to see whether the automation did the same. The App's session follows the automation's select. Nothing is written. |
| Live | The App runs the sessions: it keeps `input_select.qilowatt_session_state` and `input_boolean.emhass_automation` like the automation does, writes feed-in first and the passive-mode registers after, and when a session ends it hands the inverter straight back to the plan with one write (the automation's safe state only when no fresh plan exists). Sessions are stored, so a restart continues or ends them from the current sensors. "End session now" on the Market page is the kill switch. |

Settings → **Qilowatt market control** holds the entities and thresholds (the automation's values are the defaults). The Sofar registers and buttons come from Settings → Inverter control.

**The feed-in limit during a sell** is where EMHASS Lens deliberately differs from the automation. While selling, the inverter exports the lower of the grid target and the feed-in limit.
- **The automation** sets the limit to the commanded power on every sell, on its own 3-minute cooldown. A limit held below a rising command caps the export, so the market gets less than it asked for. A limit above the command only lets out spare PV the battery can't take.
- **EMHASS Lens changes the limit only when it has to.** A limit at or above the command is left as it is. A lower one (for example 0 W from a cheap-price slot) is raised to the sell cap (15500 W) at once, or the market would get less than it asked for.
- **It follows the command only when the battery can't take the spare PV:** the battery is at or above Thresholds → **Sell: the battery can't take spare PV from** (97 %), and PV minus the house load (Market entities → **House load now**) exceeds the command by more than the deadband. It then lowers the limit no more than once per cooldown, and raises it at once. Below that the battery takes the spare PV; a Sofar battery still took 900 W at 93 %.
- In a Kratt session on 13 October the limit would have stayed at 15500 W throughout. That saves all 7 feed-in presses (17 presses in all became 10), and the gap between delivered and commanded power would have shrunk by about 60 %.
- Each decision on the Market page says what the automation would have written. In Shadow a sell's feed-in limit isn't compared, so the agreement covers the session, the switch and the passive-mode registers.

**Session watchdog.** Next to the market control runs a safety net that does the job of the automation "Qilowatt: Session Watchdog". It shares none of the market control's decision logic and runs as its own job, so a bug, a stuck run or a refusal there (for example `input_boolean.qilowatt_automation` turned off mid-session) can't switch it off too. Every minute it checks:

- **A stuck session:** a session is open, but `sensor.qw_source` hasn't named Kratt or Fusebox for 10 minutes (or the sensor is gone). The market control ends such a session after 5 minutes itself, so this only happens when it didn't. In Live the watchdog then ends the session the way a session end does: the session select back to `none`, the EMHASS switch on, and the inverter handed back to the plan, or set to self-use when there is no fresh plan. Only the registers that differ are written, so registers that are already safe cost no EEPROM write. It sends a phone message, again every 5 minutes if clearing keeps failing.
- **A long session:** a session open for 3 hours. One phone message per session; nothing is changed.
- **EMHASS left off:** no session is open, yet the EMHASS switch has been off for 10 minutes with the inverter in Force charge or Force discharge. One phone message; nothing is changed.

In Shadow the Home Assistant automations still run the sessions, so the watchdog only records what it would clear and sends nothing. What it finds shows on the Health page and as the **Watchdog** fact on the Market page. A run is recorded under *Market session watchdog* only when something needs attention. The phone messages go to Settings → Notifications → *Mobile notify service*. The thresholds, and a switch to turn the watchdog off, are under Settings → Qilowatt market control → Session watchdog. While market control is Live, Health warns when the watchdog is turned off or hasn't checked for 3 minutes. Nothing in the App can end a session while the App itself is stopped. Turn on **Watchdog** on the App's Info tab, so the Supervisor restarts it when it crashes or stops answering. After a restart the open session is restored and ended within a minute if its source is gone.

**Moving the automation over:** 1) inverter control must be live, so that the plan can be re-applied after a session. 2) Run **Shadow** for at least a week with real sessions and watch the agreement on the Market page; 99 % or more is the bar. 3) Set Settings → Notifications → *Mobile notify service* (for the watchdog's messages) and turn on **Watchdog** on the App's Info tab. 4) With no session open, turn the Home Assistant automations "Qilowatt: Master Market Controller" and "Qilowatt: Session Watchdog" off (keep them; set the controller under Market entities → *Home Assistant automation (interlock)*) and switch to **Live**; watch the first session. Going back: set the mode to Off and turn both automations on again. Because the App mirrored the session select and the switch, the automations carry on from where things are.

What stays as it was: the automation wrote feed-in only while selling, and a command under the gate during a session ends the session rather than flipping it. What is different on purpose: a session end goes straight to the plan's targets instead of the automation's "self-use, grid 0" defaults, and a burst of three sensor updates becomes one decision.

## The ML load forecast

EMHASS forecasts the house load with a model trained on your load sensor (`load_forecast_method: mlforecaster`). The Health page's **ML load forecast** card runs **Fit**, **Tune** and **Predict**; Fit uses the same number of lags the MPC runs send, so the model forecasts the whole horizon.

**Tune** is different: EMHASS's tuner picks its own lag count from 6 h, 12 h, 1 day, 1.5 days, 2 days, 2.5 days or 3 days, and a tuned model forecasts only that far. Once tomorrow's prices and a forecast day are in, the horizon is about 2.5 days, so a model tuned to 1.5 days (144 slots) makes every run fail with "Unable to obtain 233 lags_opt values". EMHASS Lens recognises that answer, remembers how far the model reaches and plans again at once with the horizon cut to it; later runs are cut straight away. Health shows *EMHASS's load model forecasts only N slots* meanwhile. **Fit** restores the full horizon; after a day EMHASS Lens tries the full horizon again by itself, in case the model was fitted elsewhere.

**Automatic fit.** Settings → EMHASS → ML load forecast → *Fit the model automatically* (every night by default) fits the model right after the first MPC run from 03:00, so it keeps up with the house; *Fit right away when the model can't serve the runs* fits after the next run when the model is a short tuned one or the lag count changed (at most every 6 hours). Both only while EMHASS Lens drives EMHASS (live with Auto MPC); in dry run EMHASS is never touched. It never tunes. MPC runs are refused while EMHASS fits, so a slow fit costs at most one quarter's run. The Fit job on the Health page marks automatic fits.

While EMHASS computes something for EMHASS Lens (an MPC solve, a fit or a tune), it may not answer its health check in time. The Health page's EMHASS card then shows *Busy with …* instead of calling EMHASS unreachable; a refused connection still counts as unreachable.

## EMHASS versions

EMHASS Lens needs EMHASS **0.17.9** or later (the plan API). With **0.18.2** or later it no longer has to wait out the seconds around a slot boundary. **0.18.5** is recommended: the MPC horizon and the forecasts stay right across the DST changes, and a solution EMHASS calls `Optimal_Inaccurate` counts as a plan instead of an error. The Health page's EMHASS card shows the version and the configuration checks.

What EMHASS Lens uses from the 0.18 releases:

- **Running now (0.18.2).** Settings → **Inputs → Deferrable loads → Running now when** names an entity that says the load is running right now, with **Running states** listing the states that mean running, for example the ABB charger's `sensor.abb_terra_ac_charger_charging_state_raw` with `4`. EMHASS then plans a load that is on as on, instead of scheduling a fresh start with its startup penalty. Nothing is sent while the field is empty.
- **More than one battery (0.18.0).** EMHASS with `number_of_batteries` above 1 publishes `SOC_opt_0`, `SOC_opt_1`, … instead of `SOC_opt`; the Plan page, This slot and the plan-published event read them. EMHASS Lens still sends one battery SOC pair, which EMHASS applies to every battery, so the configuration check warns.
- **Horizon attributes (0.18.2).** EMHASS attaches the whole horizon to every sensor it publishes. EMHASS Lens reads the plan from the API and doesn't need that; the configuration check hints that `publish_horizon_attributes` can be turned off in EMHASS to keep Home Assistant's recorder small, unless a dashboard uses the attributes.

EMHASS-side features that work without any change here: capacity charges, thermal loads and the heat topology, VictoriaMetrics and InfluxDB history, the hybrid-inverter efficiency curves, the tariff schedule time zone and `battery_soc_final_reward_factor`. Set them in EMHASS; EMHASS Lens's runtime parameters don't touch them.

## Logs and runs

- **Logs** shows the App's log live. Every line belongs to a component, and lines written during a job carry that run's number. A strip above the lines counts them per 5 minutes over the last 3 hours, with the warnings and errors marked.
- **Runs** lists every job execution with its outcome. Above the list, the **Timeline** shows every run of the last **1 h**, **6 h** or **24 h** (the switch on its right; the choice is part of the page address) in a lane per kind of job (EMHASS, prices, inverter, …): one bar per minute, 5 minutes or 15 minutes, coloured by the most notable outcome in it (an error before a refusal before a dry run before OK). Point at a bar for what ran then; click it to open that run. On a wide screen a click shows the run beside the list; **Open run** opens it in full. Its page has three tabs: **Summary** (what happened and what the run looked at), **Artifacts** (everything it stored, as JSON) and **Logs**. For EMHASS MPC and cost-function comparison runs, the Summary starts with the **Pipeline**: building the payload, each call to EMHASS (the compared cost functions, then the live one, with EMHASS's own stages inside it: PV forecast, load forecast, price prep and the optimisation with its solve time) and reading back, as bars on one time axis, with what failed marked. Runs made before 0.4.6 are placed from when each call ended, so their bars can be off by up to a second. You can also download it all as one JSON file for a bug report. **Wrote to the inverter** keeps only the runs that wrote to the inverter: the plan's inverter decisions and the market's reconciles, which write through the same writer. To download several runs at once, tick the box before each (shift-click ticks a range, the box in the header ticks all shown), then pick **Download logs (.log)** for one text file with each run's summary, its log lines and everything it stored (as JSON), or **Download bundles (.zip)** for each run's JSON file in a zip; up to 200 runs at a time.
  - **Filter** by job and outcome: each opens a list (the jobs A–Z) where you tick any number of them. **Include** shows only the ticked ones, **Exclude** hides them (the button then reads, say, *All but 2 jobs*), and **Clear** shows everything again. Both are part of the page address.
  - **Filter** by a time range: **From** and **To** are read in Home Assistant's time zone, and **Today**, **Yesterday** and **Any time** set the range in one click. The range includes From but not To.
  - **Sort** by clicking a column header; click it again to flip the direction. Run and Started sort on the server, so "Load more" continues in that order. Job, Took and Outcome sort the runs loaded so far.
- **Recent decisions and slots** on the EV charger, Inverter and Market pages, and the Market sessions, have the same tools:
  - **Day:** "Latest" shows the newest rows. Pick a day, or step with ← and →, to load that whole day.
  - **Search** matches every word you type, and a select narrows the list to one rule, branch, kind or direction.
  - **Only where the automation differed** keeps the comparisons that disagreed.
  - **Sort** by clicking a column header.
  - The choices live in the page address, so a filtered view survives a reload and can be bookmarked.
- **Times carry their date** everywhere a list can span several days, for example "Sat, Oct 10, 18:15", with the year added when it isn't the current one.
- The same log lines appear in the App's **Log** tab in Home Assistant.
- **Pages refresh by themselves.** **Live updates** (in the status chip's panel) is one connection that delivers log lines and says when each job starts and finishes, and every page reloads what that job changed. Each page also reloads on a timer of 10 seconds to 5 minutes.
  - When the lamp is amber ("Polling every 10 s"), the live connection isn't getting through, often because a proxy buffers it. Pages keep refreshing on their timers, and the Logs page asks for new lines every 5 seconds.
  - An open run that is still running is followed every 3 seconds, with its log lines.
  - A list showing a day that has ended doesn't reload, because that day no longer changes.

## Security

- **Changes need the Home Assistant login.** Settings can only be changed through the sidebar (Ingress).
- **The direct port is off by default.** If you enable it (`8099/tcp`), it has no login and is read-only, with secrets masked.

## Data, storage and backups

EMHASS Lens keeps two SQLite files in its `/data` folder.

- **`app.db`** holds the settings and their history, Nord Pool prices, price forecasts, every EMHASS plan, the measured history, the cost-function comparisons and a few remembered facts. It is part of every Home Assistant backup. Right before a backup the App checkpoints the file and runs an integrity check (`backup_pre`), so the copy is complete and a damaged file stops the backup instead of being saved.
- **`runs.db`** holds run details, their inputs and responses, and the log. It is bulky, rebuilt over time, and left out of backups.

**Retention** (Settings → Storage → Retention) says how long things stay: logs and run details 7 days, run summaries 30 days, problem history 90 days, market sessions 180 days, and the newest 100 settings versions (older ones go only after 30 days; the current one always stays). Prices stay 120 days, forecasts and cost-function plans 30, measurements as set under Measurements, plans the newest 2000. Pinned runs keep their details and log lines for ever.

**Size budgets** (Settings → Storage) cap each file: `runs.db` 300 MB and `app.db` 200 MB by default. When the data in a file exceeds its budget, the nightly cleanup (03:30) cuts the oldest calendar day of one table at a time, in a fixed order: for `runs.db` log lines, then run details, then run summaries; for `app.db` cost-function plans, plans, measurements, forecasts, prices, inverter write records, problem history, market sessions and finally settings history. It never cuts pinned runs, open problems or sessions, the current settings version, or the last one to seven days each table needs for the planner and the accuracy card. When even that leaves a file over budget, Health says so.

**Compaction.** Deleting rows frees pages inside the file; SQLite reuses them, so the file stops growing, but it only shrinks with `VACUUM`. After each cleanup the App compacts a file that has at least 20 % and 16 MiB of free pages, provided the disk has free space of about twice the file (set Settings → Storage → Compact databases to "Only with Compact now" to stop that). Compaction pauses the App for seconds to tens of seconds.

The Health page's **Storage** card shows both files (size, data in use, free pages, budget), the biggest tables, the last cleanup, the free disk space and the newest Home Assistant backup that contains the App, with **Clean up now** and **Compact now**. Health warns when no backup containing EMHASS Lens is newer than Settings → Storage → "Warn when no backup for" (3 days by default), when a file stays over budget, and when the data disk has less than 200 MiB free.

**Restoring.** A restored Home Assistant brings `app.db` back with everything above, secrets included. Run history starts afresh: the App notices an empty `runs.db` next to an `app.db` that remembers run numbers, keeps one placeholder run so new numbers continue after the old ones, and shows a "Restored from a backup" note on the Storage card until dismissed. The agreement figures (inverter, EV charger, market) and the measured history start from scratch. The step-by-step runbook, including a rehearsal that restores a backup into a scratch copy without touching Home Assistant, is in the repository's `docs/BACKUP.md`.
